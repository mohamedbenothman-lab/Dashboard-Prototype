## 1. What the document is

A *Phase-0 approval baseline* — not a finished design. Everything is tagged with one of three markers, and the
markers are the actual content: the document deliberately avoids presenting any decision as approved.

| Marker | Meaning |
| --- | --- |
| `[P]` | Project requirement — adopted from the project plan / project-board blueprint |
| `[E]` | Recommendation — technical proposal, **not** a confirmed company decision |
| `[O]` | Open — missing evidence, assumption, or pending decision |

## 3. The architecture in one paragraph

Everything stays on-premises with egress blocked; the only paths into company data are a read-only SMB/UNC
share and a read-only ODBC link to IN-FORM. A single GPU server runs FastAPI (identity, ACL, tools),
PostgreSQL (metadata, jobs, outbox, audit), Qdrant (vectors), Ollama (local models), one indexing worker and a
separate `erp-sync` service. Rules decide, the AI only proposes, and a human confirms. The hardest constraint is
permission correctness: rights are resolved before the vector search, re-checked live before any snippet enters
the LLM context, and everything fails closed.

## 4. What blocks the pilot (the short list)

Phase-0 gates, all `[O]`:

1. **OP-04 / B** — effective SMB rights proven with at least two identities, plus a revocation test. Wi-Fi access is explicitly not accepted as identity.
2. **OP-01** — IN-FORM reality: DBMS, ODBC driver, 32/64-bit, DSN, modules, readable voucher references.
3. **OP-02** — unique project/case IDs; names are search aids only, never join keys.
4. **OP-03** — the real UNC path (the mapped drive on the workstation proves nothing about the server).
5. **OP-07** — ten real pilot cases with a named business team.
6. **OP-13 / OP-18** — DPIA, Art. 22 GDPR, works council, EU AI Act.
7. **OP-11** — shared vs. separate infrastructure with the project board.

## 5. Observations worth your attention

These are review findings, not translation issues:

1. **More `[P]` markers after the revision than before.** The QA report counts `[P]` 41 → 72, `[E]` 31 → 190,
   `[O]` 26 → 167. The document states no `[O]→[E]/[P]` upgrades happened, but the marker count grew mostly
   because traceability and the register repeat source text. If this baseline is used for sign-off, count
   *decisions*, not markers.
2. **Glossary collision on "order".** "Auftrag" is glossarised as `order`, while a separate entry `order` is
   described as a historical component of `order_file_links` with "no confirmed business definition". Two rows
   with the same term and different meanings will confuse a reader who searches the glossary for "order".
3. **Enum values are half German.** In A.5, `suggestions.status` is `draft/confirmed/dismissed` (English) while
   `risks.status` and `task_candidates.state` are `erkannt`/`in Prüfung`/`bestätigt`/`gelöst`/`verworfen`. I kept
   them exactly as in the original — but a technical contract with mixed languages is worth normalising before
   anyone implements it.
4. **A figure/asset inconsistency.** Appendix D's change report embeds Markdown image links such as
   `figures/Abb_01_Systemkontext.svg`, but no such files are part of the supplied PDF, and the document elsewhere
   says all figures were rendered as greyscale PNG at 300 dpi. The source format of the figures is therefore
   ambiguous.
5. **A metric that cannot work as written** — and the document knows it: `Recall@20 ≥ 85 %` is impossible with more
   than ~23 relevant photos (20/0.85 ≈ 23.5). Chapters 14 and A.6 admit this and propose R-precision or
   `Recall@max(20, n)` instead; the threshold itself stays `[O]`.
6. **Two targets are conflated in wording.** The "≈ 2 minutes" figure applies to the read-only ERP sync, not to
   OCR/image indexing (chapter 06 clarifies this, but the figure label in figure 8 sits next to the sync cadence).
7. **Sign-off is genuinely blank.** Author, IT, business department and DPO rows carry no names and no dates;
   the four named persons (Mike, Jan, Tobias, Tanja) explicitly get no derived roles (OP-19). Treat the document
   as a review draft, not an approved baseline.
8. **Appendix D tail is a QA dump.** Pages 74–93 list every number and every status marker with raw German
   context fragments. It is useful proof of editorial completeness, not readable architecture. It is summarised
   (with structure and purpose) in the translation rather than rendered line by line.
9. **Relationship to this repository.** The document describes a React + FastAPI + PostgreSQL + Qdrant + Ollama
   target architecture. This repo currently holds R Shiny and Streamlit prototypes (`dashboard_pro_ki.r`,
   `dashboard_simple.r`, `app.py`, `database.py`). Only `app.py`/`database.py` overlap conceptually; the SQLite
   schema there is a much smaller subset of the chapter-05 core schema. If the prototype is meant to become the
   implementation, the gap to close first is the file register, source/provenance columns and the ACL gate.
10. **No zip was attached.** The upload contained only the PDF; the "break down" you mentioned as a zip did not
    arrive. If that zip held the separate part files or the figure assets, they would let me verify points 4 and 9.

## 6. Translation conventions

- Identifiers, table/field names, endpoints, enum values and code tokens are untranslated by design.
- German business terms are translated once and used consistently: *Vorgang* → case, *Beleg* → voucher/record,
  *Anlass* → occasion, *Freigabe* → approval, *Frist* → deadline, *Datenstand* → as-of date.
- Original page numbers are retained in figure headings (e.g. "Figure 15 – Trust zones (p. 39)") so you can compare
  against the German PDF.
- Figures are reproductions of the extracted label sets plus the original legend and caption text; the diagrams
  themselves were not redrawn.
